# TG Clean v0.2.0 — agreed design

Status: approved design, implementation branch `v0.2.0-tg-auto`.

Implementation status: TG Auto transport v2 is now being compiled and tested. The first transport test includes direct WSS, an isolated Telegram-only ByeDPI process, mobile/Wi-Fi network change detection, per-network route selection, WSS endpoint racing, short-lived pools and fail-closed behavior instead of direct MTProto TCP fallback.

## Product modes

### 1. Telegram Auto
- No Android VPN.
- Telegram connects to local SOCKS5 `127.0.0.1:1082`.
- TG Auto chooses the best Telegram transport for the current network.
- Candidate order starts with direct secure WSS, then Telegram-specific ByeDPI-assisted WSS strategies, then optional additional mobile fallback if needed.
- Result is cached only for the current network identity and is re-evaluated after meaningful network changes.

### 2. Telegram + DPI VPN
- Telegram still uses the independent local `127.0.0.1:1082` transport.
- Android VPN routes ordinary device traffic through ByeDPI.
- General DPI strategy is selected separately from the Telegram transport strategy.
- User may choose a recommended/manual general DPI strategy.

### 3. Full Auto
- Telegram Auto enabled.
- Android DPI VPN enabled.
- TG Auto independently selects the Telegram transport strategy.
- DPI Auto independently tests/selects the general device DPI strategy.
- Neither selector is allowed to silently overwrite the other.

## Mobile-network requirement

Confirmed real-world symptom: direct Telegram WSS works on Wi-Fi but fails indefinitely on mobile data even after a clean app start with Wi-Fi disabled. Therefore v0.2.0 must not treat this as only a stale-socket/network-switch problem.

Required behavior:
- Detect default-network changes with Android ConnectivityManager callbacks.
- Distinguish Wi-Fi, cellular and other/default networks.
- Invalidate WSS pools, endpoint health and current TG-Auto decision when network identity changes.
- Re-probe Telegram transport on cellular instead of reusing Wi-Fi decisions.
- Cellular probing must include ByeDPI-assisted Telegram WSS strategies, not only direct WSS.

## TG Auto probing

Each candidate must report:
- success/failure;
- connect/handshake latency;
- selected Telegram DC/media class;
- endpoint/domain used;
- transport type;
- failure reason;
- whether a pool hit or new connection was used.

Candidate selection policy:
1. Prefer a healthy direct secure WSS path if it succeeds quickly.
2. Otherwise test a bounded set of Telegram-specific ByeDPI strategies.
3. Pick the fastest stable successful candidate, not merely the first response.
4. Keep direct TCP fallback disabled by default for blocked networks; expose it only as an advanced emergency option.
5. Use short adaptive backoff instead of long global blacklisting.

## WSS transport improvements

- Warm relevant Telegram DC1–DC5 main/media routes without maintaining excessive idle sockets.
- Race alternate Telegram WSS domains instead of waiting full timeout sequentially.
- Validate pooled sockets before reuse or discard aggressively after network changes.
- Keep secure TLS CA/hostname verification and WebSocket validation from v0.1.1.
- Keep SOCKS listener loopback-only and Telegram-only.

## UI principles

Main screen should expose only:
- Telegram state;
- current network (Wi-Fi / mobile);
- selected product mode;
- Telegram route + latency;
- system DPI status/strategy when relevant;
- start/stop;
- one-tap Telegram proxy setup;
- diagnostics.

Advanced/raw ByeDPI command editing remains available only behind an Advanced section.

## Telegram setup

One-tap action opens Telegram using the official SOCKS deep-link format with:
- server `127.0.0.1`
- port `1082`
- no username/password

An in-app manual instruction remains available as fallback.
